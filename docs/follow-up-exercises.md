# 课后从哪里继续改

不要同时改完整条流水线。选一个任务，保留修改前的输出，再用同一份虚构逐字稿跑一次。

## 任务一：增加一个“风险与阻塞”章节

适合第一次改 Skill。

- 输入：`examples/input/sample-meeting.md`
- 要做的事：在复盘里增加 `## 风险与阻塞`，但不要把 `待确认问题` 删除或改名。
- 需要修改：`SKILL.md`、`plugin/lib/recap.mjs`、Tool 参数和合同测试。
- 交付：修改前后的 `meeting-recap.md`、测试结果和一段说明。

检查：缺少新章节时测试会失败；“标签颜色待确认”仍然留在待确认问题中。

## 任务二：增加 DOCX 导出

适合练习 Tool 的责任。

- 输入：已经生成的 `runtime/meeting-recap.md`。
- 要做的事：新增 `export_recap_docx`，不得让模型重新写复盘。
- 交付：Tool 注册、确定性导出函数、一个真实 `.docx` 和合同测试。

检查：DOCX 与 Markdown 的标题和条目一致；删除 `meeting-recap.md` 后，Tool 明确失败。

## 任务三：接一个真实 ASR 适配器

适合已经有转写服务的人。

- 先阅读 [media-adapter.md](media-adapter.md)。只使用你有权上传的脱敏录音。
- 交付：适配器说明、脱敏输入、`media-transcript.json`、标准逐字稿和一次失败记录。

检查：说话人或文本为空时适配器失败；听不清的信息没有被模型补成确定事实。

## 任务四：增加第二个消息渠道

适合练习输出适配器和 Hook。

- 可以选择企业微信、Slack 或你自己的本机 Mock。先实现“准备消息”，再实现“发送消息”。
- 交付：消息 JSON、发送前批准判断、成功回执和接收端拒绝时无成功回执的测试。

检查：新渠道仍然读取 `meeting-recap.md`；未经批准不会发出请求；生产地址不能混进默认测试配置。

## 提交时附上这四样东西

1. 你改了哪一层，为什么是这一层。
2. 修改前的输出或失败现象。
3. 最小修改内容。
4. 同一份输入再次运行后的结果。

只有最终文件，没有修改前后的运行记录，很难判断 Skill 是真的变稳了，还是这一次碰巧写对了。

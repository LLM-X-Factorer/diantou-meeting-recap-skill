# `SKILL.md` 为什么这样写

真正运行的文件在 [`.dsh/skills/meeting-recap/SKILL.md`](../.dsh/skills/meeting-recap/SKILL.md)。这里不参与 Harness 调用，只负责解释那份文件。

先记住一个区别：`SKILL.md` 不是程序代码，也不是写给学员看的完整教程。它是在模型接到任务时，补给模型的一份工作说明。Tool 才负责读写文件、渲染 PDF 和发送卡片。

## 文件开头：让 Harness 找到它

```yaml
name: meeting-recap
description: 把已脱敏的会议逐字稿、录音或视频整理成可核对的会议复盘……
```

- `name` 决定用户输入的 `/meeting-recap`。
- `description` 决定模型和用户在什么任务里会想到它。这里同时写了能力和边界，没有写成“处理所有会议相关工作”。
- Harness 在省略调用策略字段时，默认同时允许用户显式调用和模型发现。因此这里不重复写默认值，也让这份 Skill 更容易通过其他基础校验器。

如果把 description 写得很宽，例如“处理会议”，它很容易抢走不属于自己的任务；如果只写“生成纪要”，模型又不知道它还负责 PDF、卡片和发送边界。

## 完成标准：先说会留下哪些文件

Skill 没有从概念讲起，而是先列出：

```text
runtime/normalized-transcript.md
runtime/meeting-recap.md
runtime/meeting-recap.pdf
runtime/feishu-card.json
```

这几行让“完成”变成可以检查的事实。模型说“已经整理好了”不算完成，对应文件存在而且内容通过验证才算。

回执单独处理：只有接收端成功以后才出现 `feishu-receipt.json`。被拒绝的请求不能留下一个容易被误读成成功的回执。

## 输入路线：为什么文本和媒体要分开

`.md`、`.txt` 直接规范化，不需要上传，也不该先试 ASR。音频和视频可能进入第三方转写服务，所以需要用户知道并允许。

两条路线最后都会得到 `normalized-transcript.md`。从下一步开始，复盘代码只面对同一种输入，不需要反复判断来源是文字、录音还是视频。

## 先读取，再保存

Skill 要求先调用 `load_normalized_transcript`，再调用 `save_meeting_recap`。这不是为了让步骤看起来完整。

加载 Tool 会在当前 Harness 会话里保存逐字稿哈希。保存 Tool 再读取一次文件并比较哈希。这样能拦住两种错误：

1. 模型没有读当前逐字稿，就凭旧上下文生成复盘。
2. 模型读完以后，输入文件又被别的进程改过。

哈希由 Tool 保管，不要求模型复制。模型擅长理解内容，不适合充当完整性存储。

## “待确认”不是一句写作要求

会议里经常出现这种话：

> 我会后问运营，但现在不要在纪要里写成运营负责。

如果最终复盘写成“运营负责邀请用户”，文本看起来更完整，事实却被改了。因此 Skill 明确要求负责人、日期、决定和授权缺失时继续写 `待确认`。

这条规则同时出现在样例和测试里。只有写在 Skill 里但没有失败样例，仍然无法证明实现会遵守它。

## 为什么 Markdown 是唯一内容真源

模型只生成一次内容，保存为 `meeting-recap.md`。PDF 和飞书卡片只做确定性转换。

如果三个产物各让模型概括一次，很容易出现 Markdown 写“负责人待确认”，卡片却写成“运营负责”。单一真源不是文件格式偏好，而是在减少互相矛盾的答案。

## 发送放在最后

`prepare_feishu_card` 只是准备 JSON，不会产生外部影响。`publish_feishu_card` 才会发送，所以它经过 `tools/pre-execute` Hook。

Skill 明确写了拒绝、取消、缺少凭据和旧回执都不算成功。真正的成功证据是：

```text
Tool 返回 delivered: true
+ 本次生成新的 feishu-receipt.json
```

## 为什么教学解释不直接写进 `SKILL.md`

你正在读的这些解释如果全部塞进运行文件，每次调用都会占用模型上下文，还可能把“课堂上要讨论什么”误当成任务步骤。

所以两份文件分工：

- 运行文件只保留会改变模型决定的规则。
- 本文解释这些规则从哪里来、拦住了什么错误。

改动运行文件后，记得同步检查本文和合同测试；不要维护两套不同的行为要求。
